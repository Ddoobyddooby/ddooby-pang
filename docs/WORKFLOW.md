# 작업 방식 (Claude 개발팀 + 필요할 때 Codex)

> 사용자(고객·제품 최종 결정자), Claude 메인(상시 PM·PL)·claude-1·claude-2(시니어 개발자), 필요한 시점에만 부르는 Codex의 협업 절차. 어느 PC에서 clone해도 역할은 같다.
> Claude 메모리(`~/.claude/…`)는 PC마다 따로라서 규칙은 여기에 둔다.
>
> **탭 구성과 위임 순서는 `CLAUDE.md` "작업 위임 흐름"이 우선한다.** Codex의 권한 경계와 결과 파일 공통 형식은 `AGENTS.md`가 기준이다. 이 문서는 요청서 형식·투입 기준·산출물·검증 절차를 적는다. "메인"은 Claude 메인(PM·PL), "코딩 탭"은 claude-1·claude-2를 뜻한다.

## 1. 기본 방식과 예외

| 방식 | 언제 | 하는 일 |
|---|---|---|
| **기본 팀** | Ddooby-Pang 기획·수정·기능 추가 요청 | Claude 메인이 접수·요구사항·설계·배분·검증·보고, claude-1·2가 구현. Codex는 8절 기준에 맞을 때만 한 역할로 부른다 |
| **특정 탭에 직접 요청** | 사용자가 담당 탭을 명시했을 때 | 사용자 지시를 우선한다. 담당 범위와 Git·검증 규칙은 `AGENTS.md` 또는 `CLAUDE.md`를 따른다 |

2026-11-08 이전에는 Codex PM이 요청 접수·SPEC·최종 보고를 맡았다. 이제 그 일은 Claude 메인이 하고, Codex 탭(기존 codex-PM 탭)은 8절의 전문 역할만 맡는다.

## 2. 역할

- **Claude 메인 (PM·PL)**: 사용자 요청을 상시 받아 제품 요구사항을 정리하고 사용자와 결정한다. `SPEC.md`·`docs/PLAN.md`·`docs/TASKS.md`·설계 문서(`docs/superpowers/`)를 관리한다. 코딩 탭에 작업을 나눠 지시하고, Codex가 필요하면 8절대로 부른다. 결과·지적을 확인해 통합·검증하고, `docs/DEVELOPMENT.md` 4·6절과 TASKS 체크를 반영한 뒤 사용자에게 보고한다. 제품 코드는 사용자가 "간단 수정"을 직접 지시한 예외 외에는 코딩 탭에 맡긴다
- **코딩 탭 (claude-1·2)**: 받은 지시서대로 코드·테스트를 쓰고 자기 브랜치에 커밋한다. 메인의 지시를 받고 main에 반영·push한다. `docs/`, `CLAUDE.md`, `AGENTS.md`는 고치지 않는다 (지시서에 적힌 경우만 예외)
- **Codex (테스트 전략·실패 분석·독립 리뷰·디자이너)**: 8절. 코드·문서 수정, 커밋, push, 원격 변경은 하지 않는다
- 두 코딩 탭이 같은 파일을 동시에 고치지 않게 메인이 작업을 나눈다

## 3. 탭 찾기

- 역할별 Orca 탭 제목은 `CLAUDE.md` 표에 있다. 탭 ID·handle은 PC나 Orca 세션마다 달라지므로 적어 두지 않고, 지시 전에 `orca terminal list --worktree current --include-visual-layouts --json`으로 탭 제목이 일치하는 handle을 확인한다
- Claude 메인에서 Claude 세션 간 `ListAgents`를 쓸 때는 같은 PC의 세션 이름을 확인한다. 메시지 주소는 세션 이름(예: `ddooby-pang-22`)이다
- 사용자가 Orca `orcaTabId`로 알려주면 macOS에서는 다음으로 대조한다:
  `~/.claude/sessions/<pid>.json`의 `name` ↔ `ps -Eww -p <pid>`의 `ORCA_TAB_ID`
- 세션 이름은 탭을 새로 열 때마다 바뀐다. 위임할 때마다 다시 확인한다
- 메시지는 **같은 PC 안의 세션끼리만** 오간다. 메인과 코딩 탭은 같은 PC에서 연다
- 모든 탭의 권한 모드를 같게(예: auto) 둔다. 다르면 메시지가 사용자 승인 대기로 묶인다

## 4. 코딩 탭 지시서

메인은 기술 계획을 세운 뒤 코딩 탭에 자기완결형 지시서를 보낸다. 첫 줄은 한 문장 요약. 담을 것:

1. **태스크 ID와 범위**: `TASKS.md`의 ID, 관련 설계 문서 경로
2. **작업 폴더·브랜치·포트**: 아래 5절
3. **할 일**: 파일, 함수 이름·시그니처, config에 둘 값. 건드리지 말 곳(`src/core` 등). Codex 테스트 전략을 받았다면 그중 구현할 검증 항목
4. **확인**: `npm run lint && npm run typecheck && npm test && npm run build`, 브라우저 확인 항목(`?demo`, `?seed=N`, DEV 키), DEV `view ≠ board` 에러 0
5. **커밋·반영**: 커밋 메시지, 검증 통과 뒤 main 반영 절차 (`CLAUDE.md` "작업 위임 흐름")
6. **보고 내용**: 바뀐 값, 커밋 해시, 스크린샷 경로, 사용자 확인 절차, 공부 포인트(메인이 DEVELOPMENT 6절에 옮긴다)

## 5. 코딩 탭의 Git 흐름

메인 폴더는 `main`을 쓰고 사용자의 dev 서버(5173)가 떠 있을 수 있다. 코딩 탭은 **자기 worktree**에서 일한다.

```bash
# 처음 한 번 (메인 폴더에서; 현재 태스크 예시)
git worktree add ../ddooby-pang-A -b feat/v2-w1-01-combo-core origin/main

# 구현 탭: 작업·검증 → 자기 브랜치에 커밋 → 메인에 커밋 해시 보고
# Claude 메인: diff·완료 기준 확인 → (8절 기준이면) Codex 독립 리뷰 → 지적 수정·재리뷰

# 검증 통과 후 메인의 반영 지시를 받은 구현 탭만 실행
git fetch origin && git rebase origin/main
npm run lint && npm run typecheck && npm test && npm run build
git push origin HEAD:main

# 다음 태스크 시작 시 (worktree 안에서, main 반영을 확인한 뒤; 예시)
git fetch origin && git switch -c feat/v2-w1-02-combo-view origin/main
```

- worktree에서는 `main`을 체크아웃할 수 없어서(메인 폴더가 쓰는 중) 검증 통과 후 rebase하고 `HEAD:main`으로 push한다
- dev 서버 포트: 탭 A `5174`, 탭 B `5175`. 5173은 사용자 것이라 끄지 않는다
- 브라우저 자동화(Playwright)는 프로필을 같이 쓴다. 확인이 끝나면 브라우저를 닫는다
- 일이 끝나면 메인이 worktree와 브랜치를 지운다: `git worktree remove ../ddooby-pang-A && git branch -D <브랜치>`

## 6. Claude 메인의 검증과 보고

1. 구현 탭의 커밋 해시·스크린샷을 받고, diff를 설계 문서·`CLAUDE.md` 아키텍처 규칙·완료 기준과 대조한다
2. 8.1 기준에 맞으면 Codex 독립 리뷰를 요청하고(8.4), 고칠 지적은 구현 탭에 되돌린다. 리뷰를 생략하면 이유를 TASKS 확인 메모나 완료 보고에 한 줄 남긴다
3. 검증 통과 뒤 구현 탭에 rebase → lint·typecheck·test·build → `HEAD:main` push를 지시한다
4. 메인에서 반영 결과를 확인하고, `TASKS.md` 체크·`DEVELOPMENT.md` 4절(확인 방법)·6절(Study for App)을 추가한다
5. 변경 사항·검증 결과·사용자가 직접 확인할 방법·미확인 사항을 사용자에게 직접 보고한다

## 7. 모델 고르기

- 게임 규칙이 들어가는 `src/core` 작업(특수 블록 연쇄, 점수, 미션 판정 등)은 Opus, 화면·연출·HUD는 Sonnet으로 충분하다
- 모델은 지시서로 바꿀 수 없다. 사용자가 그 탭에서 `/model`로 바꾸거나 `claude --model opus`로 새 탭을 연다. 메인은 맡기기 전에 사용자에게 알려준다

## 8. Codex 함께 쓰기

Codex는 상주 역할이 아니다. 메인이 필요한 시점에 **한 요청에 한 역할**로 부르고, 결과는 `.codex-out/` 파일로 받는다. 역할별 권한 경계와 결과 파일 공통 형식은 `AGENTS.md`가 기준이다 (Codex는 저장소 루트의 `AGENTS.md`를 자동으로 읽는다).

### 8.1 언제 부르나 (선택적 투입)

| 상황 | 역할 | 시점 |
|---|---|---|
| 게임 규칙·수용 기준이 복잡하거나 경계 조건이 많다 | 테스트 전략 설계자 | 태스크 초반, 코딩 탭 지시 전 |
| 같은 실패가 반복되거나 원인이 불명확하다 | 실패 분석·트리아지 | 메인이 1차로 원인을 못 찾았을 때 |
| 데이터 무결성, 보안, 온라인·오프라인 동작, 게임 진행 핵심 경로(`src/core`, `src/modes`, 저장 형식, 서버 판정), 큰 리팩터 등 회귀 영향이 큰 변경 | 독립 리뷰어 | 구현 커밋 뒤, main 반영 전 |
| 새 화면·시각 에셋이 필요하다 | 디자이너 | 구현 지시 전 (사용자가 시안을 고른다) |

- 위에 해당하지 않는 단순하고 범위가 좁은 변경(문구, 값 조정, 문서·에셋만 바뀐 커밋 등)은 메인이 자체 검증하고 Codex를 부르지 않는다. 리뷰를 생략하면 이유를 남긴다 (6절 2)
- Codex 한도로 결과를 받지 못하면 사용자에게 알린다. 사용자가 정하면 메인이 같은 기준으로 대신 검토하고, 결과 파일에 "Claude 메인 대리, 독립 리뷰 아님"을 적는다

### 8.2 요청서 공통 형식

첫 줄은 한 문장 요약, 그다음 "AGENTS.md와 docs/WORKFLOW.md 8절을 따른다. 파일 수정·커밋·push·원격 변경 금지"를 넣는다. 저장소 전체나 지난 대화를 요약하지 않고 아래만 준다.

1. **역할** 하나 (테스트 전략 / 트리아지 / 리뷰 / 디자인)
2. **기준**: 태스크 ID, 기준 커밋·브랜치(리뷰는 `<기준>...<대상>` 범위), 대상 파일
3. **참고 문서 절**: SPEC·PLAN 절, `AGENTS.md` 아키텍처 규칙 등 필요한 것만
4. **입력 자료**: 트리아지는 실패 로그 원문(명령·출력·환경), 리뷰는 메인이 이미 돌린 검증 결과와 받아들인 설계 변경
5. **금지 작업**: 위 공통 문구 + 역할별 추가 제한
6. **결과 형식·경로**: `.codex-out/<태스크ID>-<test-plan|triage|review|image>.md`, 첫 줄 판정, 근거 표기 (`AGENTS.md` "결과 파일 공통 형식")

### 8.3 테스트 전략

- **받는 것**: 위험한 경계 조건 목록, 검증 항목별 기대 결과, 단위 테스트·브라우저 확인·시뮬 중 어디서 볼지, 우선순위
- **받지 않는 것**: 테스트 코드. 메인이 항목을 골라 코딩 탭 지시서(4절 3·4)에 넣고, 작성·실행은 코딩 탭이 한다
- 메인은 받은 항목 중 버린 것과 이유를 완료 보고에 한 줄 남긴다

### 8.4 독립 리뷰

- **지시서에 넣을 것**: 기준·대상 커밋과 태스크 ID, 기준 문서(`AGENTS.md` 아키텍처 규칙, SPEC·PLAN 해당 절, TASKS 완료 기준), 찾을 것(버그, 회귀, 엣지 케이스, 빠진 테스트, 수용 기준 누락), 메인이 받아들인 설계 변경(문제가 있으면 지적), 결과 파일 경로
- **재리뷰**: 최대 2회. 이전 지적의 해결 여부와 그 수정의 회귀만 보게 하고, 같은 결과 파일에 `## 재리뷰 N`으로 덧붙인다. 2회를 넘으면 메인이 사용자에게 보고한다
- **거르기**: 메인이 지적마다 코드를 열어 확인한다
  - 맞고 바로 고칠 것 → 코딩 탭에 수정 지시 (`[fix] <태스크ID> ...`)
  - 맞지만 지금 안 고칠 것 → `docs/FEEDBACK.md` 2절에 `R<번호>`로 적고 근거에 "Codex 리뷰"
  - 틀린 지적 → 버린다 (이유를 사용자 보고에 한 줄)
- Codex 탭을 못 쓸 때는 메인이 Codex CLI에 같은 읽기 전용 요청을 보낼 수 있다:

  ```bash
  codex exec -s read-only -o <결과.md> "<요청서>"
  ```

  `codex review --commit <해시>`는 지시문(PROMPT)을 같이 받지 못해서(CLI 0.165) `codex exec`를 쓴다. 한 번에 몇 분 걸린다

### 8.5 실패 분석·트리아지

- 메인이 실패 로그(명령, 전체 출력, 커밋, 환경)와 관련 파일 경로를 준다. 사용자가 로그를 지정했으면 그 로그만 쓴다
- Codex는 그 로그와 관련 코드만 읽는다. 저장소 전체를 조사하지 않고, 파일도 고치지 않는다. 더 넓은 조사가 필요하면 그 이유와 넓힐 범위를 결과 파일에 적고 멈춘다. 메인이 승인하면 이어서 본다
- 결과 순서: 증거와 관련 범위(본 로그·파일) → 가능성 높은 원인부터(가설별 근거·반증) → 다음 확인 절차·수정 제안 → 고친 뒤의 검증 방법
- 고치는 일은 메인이 원인을 확인한 뒤 코딩 탭에 맡긴다

### 8.6 디자인·이미지

- **무엇**: 화면 시안, 앱 아이콘, 배경·장식, 결과 화면 그림 같은 원본. 블록(말랑 친구들)은 2026-11-03 사용자 결정으로 **몸통만** 그림으로 받는다. 얼굴(3표정)·특수 배지는 코드로 겹쳐 그린다 (v0.1 PLAN 2절 3번)
- **요청**: 메인이 디자이너 탭에 보낸다. 담을 것: 쓰는 곳, 크기(px)·비율, 투명 배경 여부, 테마(달콤 디저트, 말랑하고 둥근 파스텔, `THEME` 색), 기존 디자인 지침, 글자 넣지 않기, 다른 게임·캐릭터를 닮게 하지 않기 (저장소가 공개라서 저작권 있는 그림은 안 된다)
- **흐름**: 디자이너가 원본을 `assets/<용도>-src/`에 저장하고 파일 목록·프롬프트 요약·날짜를 `.codex-out/<태스크ID>-image.md`에 적는다 → 사용자가 보고 고름 → 메인이 코딩 탭에 연결 지시 → 코딩 탭이 크기를 맞춰 `public/`에 넣고 연결 → 출처를 그 폴더의 `CREDITS.md`에 "Codex(OpenAI) 생성, 날짜, 프롬프트 요약"으로 적는다
- 고르지 않은 후보는 저장소에 넣지 않는다

### 8.7 보내기와 받기 (Orca)

- Codex 탭과 디자이너 탭의 탭 제목은 `CLAUDE.md` 표에 있다. 터미널 handle은 Orca를 다시 켜면 바뀌므로 맡길 때마다 탭 제목으로 다시 찾는다. 연결할 수 없으면 요청서를 사용자에게 전달해 수동 입력할 수 있게 한다:

  ```bash
  orca terminal list --worktree current --include-visual-layouts --json   # visualLayouts에서 탭 제목이 일치하는 handle
  orca terminal read --terminal <handle> --screen --json        # 쉬는 중인지 먼저 본다
  orca terminal send --terminal <handle> --text "<요청서>" --enter --wait-submit 10 --json
  orca terminal wait --terminal <handle> --for tui-idle --timeout-ms 900000 --json
  ```

- 이전 요청과 무관한 일이면 Codex 탭에서 새 대화(`/new`)로 시작해 맥락을 줄인다. 작업 중에는 `/new`가 거절되므로 쉬는 중일 때 보낸다
- 코딩 탭(Claude)의 worktree·브랜치는 건드리지 않게 한다. 리뷰는 `git show <해시>`·`git diff`로 본다

### 8.8 쓰는 양

- Plus 요금제 한도가 있다. 리뷰는 태스크 커밋 묶음 하나씩, 이미지는 한 번에 후보 2~4장으로 요청한다. 한 요청에 여러 역할을 섞지 않는다
